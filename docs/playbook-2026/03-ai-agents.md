## 6장. 조달 AI 에이전트 4종

### 6.1 설계 원칙

| 원칙 | 내용 |
|------|------|
| **Human-in-the-Loop** | AI는 추천·검증·초안까지. 발주 발송·대금 지급·공급사 제재는 사람이 승인 |
| **근거 제시(Explainability)** | 모든 권고에 "왜"를 함께 표시(비교 기준가, 사용 데이터, 해당 룰) |
| **설정 기반 임계값** | 편차 기준·승인 한도·점수 가중치는 코드에 하드코딩하지 않고 고객사·품목군별 설정으로 관리 |
| **감사 가능성** | 입력·출력·모델 버전·승인자를 모두 로그로 저장 |
| **보수적 기본값** | 데이터가 부족하면 "판단 불가"로 표시하고 사람에게 넘김(억지 판단 금지) |
| **피드백 루프** | 사용자의 수용/거절/수정을 기록해 모델·룰 개선에 사용 |

### 6.2 에이전트 ① 공급사 추천 (Supplier Recommender)

| 구분 | 내용 |
|------|------|
| **트리거** | 견적 요청 생성, 입찰 공고 생성 |
| **입력** | 품목코드·규격·수량·납기·납품지, 공급사 마스터, 거래 이력, Trust Score |
| **처리** | ① 품목 취급 가능 공급사 필터 → ② 납품 가능 지역·납기 필터 → ③ 점수 산정·순위화 → ④ 다양성 보정(기존 거래처만 몰리지 않게) |
| **출력** | 추천 공급사 Top-N + 추천 사유, "신규 발굴" 표시 |
| **사람 개입** | 담당자가 추가·제외 가능, 제외 사유 기록 |

**추천 점수 구성(가중치는 설정값)**

| 요소 | 설명 |
|------|------|
| 품목 적합도 | 해당 품목·규격 취급 이력, 카탈로그 일치도 |
| Supplier Trust Score | 납기 준수율·품질 클레임·가격 안정성·거래 이력 |
| 응답성 | 견적 회신율·평균 회신 시간 |
| 거리·물류 | 납품지까지 거리, 운반 가능 여부 |
| 가격 경쟁력 | 과거 낙찰가의 시세 대비 수준 |
| 집중도 보정 | 특정 공급사 쏠림 방지를 위한 감점/가점 |

### 6.3 에이전트 ② 단가 검증 (Price Validator)

| 구분 | 내용 |
|------|------|
| **트리거** | 견적 접수, 발주 초안 생성, 단가 계약 갱신 |
| **입력** | 견적 단가, 품목·규격·수량·지역·시점, GPI 시세, 자사 과거 거래, 공시 단가 |
| **처리** | ① 비교 가능한 기준 데이터 선별(규격·수량 구간·지역·기간 일치) → ② 기준가 산출(중앙값 등 이상치에 강건한 통계) → ③ 편차율 계산 → ④ 등급 판정 |
| **출력** | 기준가, 편차율, 등급(정상/주의/경고/판단불가), 근거 데이터 건수·기간 |
| **사람 개입** | "경고"는 승인 전 사유 입력 필수, 재협상 요청 버튼 제공 |

**등급 판정 로직(개념)**

```
편차율 = (견적 단가 − 기준가) / 기준가

if 비교 데이터 건수 < 최소표본(설정값)     → 판단불가 (사람 검토)
elif 편차율 ≤ 주의임계(품목군별 설정값)      → 정상
elif 편차율 ≤ 경고임계(품목군별 설정값)      → 주의
else                                       → 경고 (사유 입력 필수)

* 기준가보다 지나치게 낮은 단가도 "저가 이상"으로 별도 표시
  (품질 미달·규격 상이·덤핑 가능성)
```

**에러 가능성과 대응**

| 위험 | 원인 | 대응 |
|------|------|------|
| 오탐(정상을 경고로) | 규격·수량 구간 불일치, 운반비 포함 여부 차이 | 총 도착가 정규화, 비교 키 엄격 일치 |
| 미탐(과다 단가 통과) | 과거 단가 자체가 높았음 | 외부 시세(GPI) 병행, 타 현장 비교 |
| 급등기 판단 왜곡 | 오래된 기준 데이터 | 기준 기간 가중치(최근 데이터 우선), 시세 변동 알림 |
| 데이터 부족 | 특수 자재·신규 품목 | "판단불가" 처리 후 사람 검토 |

### 6.4 에이전트 ③ 이상거래 탐지 (Anomaly Detector)

| 구분 | 내용 |
|------|------|
| **트리거** | 발주·승인·검수·정산 이벤트 발생 시 실시간 + 일 배치 |
| **입력** | 거래 이벤트 로그, 공급사 마스터(사업자·계좌·대표자·연락처), 사용자 권한·승인 이력 |
| **처리** | ① 룰 기반 탐지(7장 룰북) + ② 통계 기반 이상치 탐지(사용자·공급사·품목별 평소 패턴 대비 이탈) |
| **출력** | 이상 알림(위험도·해당 룰·관련 거래 묶음), 조사 케이스 생성 |
| **사람 개입** | 감사·준법 담당자가 케이스 검토 → 정상 종결/조치. **자동 제재 금지** |

> ⚠️ 이상거래 탐지는 "부정의 증거"가 아니라 **"확인이 필요한 신호"** 입니다. 알림 대상자에게 불이익을 주기 전에 반드시 사람이 사실관계를 확인해야 하며, 알림 열람 권한은 감사·준법 담당자로 제한합니다.

### 6.5 에이전트 ④ 발주 자동화 (Order Automator)

| 구분 | 내용 |
|------|------|
| **트리거** | 낙찰 확정, 단가 계약 품목 재발주 요청, 소요 계획의 발주 마감일 도래 |
| **입력** | 선정 공급사·단가, 소요 계획, 전결 규정, 공급사 계약 조건 |
| **처리** | ① 발주서 초안 생성 → ② 필수 필드·단가 검증 결과 첨부 → ③ 이상거래 사전 점검 → ④ 전결 규정에 따른 승인 경로 결정 |
| **출력** | 승인 대기 발주서, 승인 후 공급사 전송·ERP 전표 생성 |
| **사람 개입** | 승인권자 승인 없이는 발송 불가. 단가 "경고"·이상 알림이 있으면 상위 승인으로 자동 상향 |

### 6.6 에이전트 협업 흐름

```
[소요 계획] ──▶ ① 공급사 추천 ──▶ 견적 접수 ──▶ ② 단가 검증
                                                    │
                                                    ▼
[공급사 전송/ERP] ◀── 승인 ◀── ④ 발주 자동화 ◀── 선정/낙찰
        │                         ▲
        ▼                         │
   납품·검수·정산 ──────────▶ ③ 이상거래 탐지 (전 단계 상시 감시)
```

### 6.7 데이터 계약(인터페이스 초안, TypeScript)

에이전트 간 주고받는 데이터의 최소 형태입니다. 임계값은 `PolicyConfig`로 주입해 하드코딩을 피합니다.

```ts
type PriceGrade = "NORMAL" | "CAUTION" | "WARNING" | "UNDETERMINED";

interface PolicyConfig {
  readonly minSampleSize: number;
  readonly cautionThreshold: number; // 품목군별로 주입
  readonly warningThreshold: number;
}

interface PriceCheckInput {
  readonly itemCode: string;
  readonly quotedUnitPrice: number;
  readonly referencePrices: readonly number[];
}

interface PriceCheckResult {
  readonly grade: PriceGrade;
  readonly referencePrice: number | null;
  readonly deviationRate: number | null;
  readonly sampleSize: number;
}

const median = (values: readonly number[]): number => {
  const sorted = [...values].sort((a, b) => a - b);
  const mid = Math.floor(sorted.length / 2);
  return sorted.length % 2 === 0 ? (sorted[mid - 1] + sorted[mid]) / 2 : sorted[mid];
};

export const checkPrice = (input: PriceCheckInput, policy: PolicyConfig): PriceCheckResult => {
  const sampleSize = input.referencePrices.length;
  if (sampleSize < policy.minSampleSize) {
    return { grade: "UNDETERMINED", referencePrice: null, deviationRate: null, sampleSize };
  }
  const referencePrice = median(input.referencePrices);
  if (referencePrice <= 0) {
    return { grade: "UNDETERMINED", referencePrice: null, deviationRate: null, sampleSize };
  }
  const deviationRate = (input.quotedUnitPrice - referencePrice) / referencePrice;
  const grade: PriceGrade =
    deviationRate <= policy.cautionThreshold ? "NORMAL"
    : deviationRate <= policy.warningThreshold ? "CAUTION"
    : "WARNING";
  return { grade, referencePrice, deviationRate, sampleSize };
};
```

> 실제 구현은 `ai/` 폴더에서 진행하며, 위 코드는 요구사항 이해를 위한 참조 스케치입니다(저가 이상 판정·비교 키 정규화는 미포함).

## 7장. 이상거래 탐지 룰북

임계값(N, X%, 기간 등)은 모두 **고객사별 설정값**이며, 초기에는 보수적으로 두고 오탐률을 보며 조정합니다.

| ID | 패턴 | 탐지 기준(개념) | 위험 | 대표 의심 시나리오 |
|----|------|---------------|------|------------------|
| R1 | **발주 쪼개기** | 동일 공급사·품목, 짧은 기간 내 승인 한도 직하 금액 발주 반복 | 높음 | 전결 한도 회피 |
| R2 | **단가 급변** | 동일 공급사·품목 단가가 직전 거래 대비 급상승 | 중간 | 사후 단가 인상, 담합 |
| R3 | **시세 대비 과다 단가 승인** | 단가 검증 "경고" 건이 사유 없이/반복 승인 | 높음 | 특정 업체 밀어주기 |
| R4 | **입찰 담합 의심** | 응찰가가 비정상적으로 근접, 낙찰자 순환, 동일 응찰자군 반복 | 높음 | 들러리 입찰 |
| R5 | **공급사 정보 중복** | 서로 다른 공급사가 계좌·대표자·연락처·주소 공유 | 높음 | 위장 업체, 들러리 |
| R6 | **특정 공급사 집중** | 특정 담당자의 발주가 한 공급사에 과도 집중 | 중간 | 유착 |
| R7 | **직무 분리 위반** | 요청자=승인자 또는 발주자=검수자 | 높음 | 내부 통제 우회 |
| R8 | **중복·과다 청구** | 동일 금액·일자·공급사 청구 반복, 청구 수량 > 검수 수량 | 높음 | 이중 지급 |
| R9 | **검수 없는 정산** | 검수 기록 없이 정산 요청·승인 | 높음 | 허위 납품 |
| R10 | **비정상 시간대 처리** | 심야·휴일 승인이 평소 패턴 대비 급증 | 낮음 | 통제 회피(단독으로는 약한 신호) |
| R11 | **신규 공급사 즉시 대형 거래** | 등록 직후 대형 발주·선급금 | 중간 | 위장 업체 |
| R12 | **공급사-임직원 이해관계** | 공급사 정보와 임직원 정보 일치(사전 동의된 범위 내 대조) | 높음 | 이해상충 |

**운영 프로세스**

1. 알림 발생 → 위험도별 큐 분류(높음: 당일 검토, 중간: 주간, 낮음: 월간 패턴 분석)
2. 감사 담당자가 관련 거래 묶음·근거 확인
3. 결론 기록: 정상 종결(사유) / 소명 요청 / 조치
4. 정상 종결 사유를 룰 튜닝에 반영(오탐 감소)
5. 월간 리포트: 룰별 발생·확정·오탐 건수

> 개인 정보를 대조하는 룰(R5, R12)은 개인정보 보호법 등 관련 법령과 사내 규정에 따른 **목적·범위·동의** 검토 후 적용합니다(12장).
